# ADR-0060: The Virtualmin API User Is a Master Administrator, Locked Down

- Status: Accepted
- Date: 2026-10-14
- Authors: PRAHO maintainers
- Related: #347, #348, #498, ADR-0033 (credential vault), ADR-0051 (hosting account state)
- Supersedes: the "dedicated ACL user, never master admin" design of #347

## Context

Each node PRAHO deploys gets one Webmin user, `praho-api`, and Platform calls Virtualmin's remote API (`remote.cgi`) as that user. #347 intended it to be a dedicated ACL user that is never a master administrator, created with `virtualmin create-admin --can-create --can-edit`.

The Docker lab (`deploy/virtualmin-lab`, Virtualmin 8.3.0) showed that this cannot work.
- **`create-admin` makes the wrong kind of user.** It creates an extra administrator of one virtual server: it needs `--domain` and has no `--can-create` or `--can-edit` flag, so every deploy failed.
- **The remote API is scoped by role.**
  - `can_remote($program)` is `master_admin() || can_remote_as_user($program)`.
  - The non-master branch needs `can_use_remote_api()`: master, reseller, or a domain owner with `edit_remote_api`.
  - It then runs a registered command only through that command's capability check against domains the caller may edit (`remote_api_can_domain`).
  - A non-master caller therefore acts only on its own servers. PRAHO creates, lists, migrates and restores servers across every owner on the node.
  - `master_admin()` is simply "the user's virtual-server ACL has no `noconfig`".
- **Backups need master.**
  - `can_backup_domains()` and `can_backup_virtualmin()` return `master_admin()`.
  - `backup-domain --mkdir`, which PRAHO uses to create its private staging directory, is refused to anyone else ("only available to the master administrator").
- **Restores need master.** `can_restore_domain()` returns 1 only for the master admin. A reseller gets 2, a restore limited to "dir and MySQL", and a domain owner gets less. A full disaster-recovery restore needs every feature.
- **Resellers are not available.** They are a Virtualmin Pro feature; PRAHO nodes run GPL.

## Decision

`praho-api` is a Virtualmin master administrator, and the compensating controls below are mandatory. The node playbooks fail closed without them.

1. **Only the virtual-server module.**
   - The helper `playbooks/files/praho-webmin-api-user.pl` creates a Webmin user whose only Webmin module is virtual-server.
   - Its ACL starts from Virtualmin's shipped default ACL, with `noconfig=0`.
   - It cannot use Webmin's other modules: the file manager, the shell, users, packages and the rest.
2. **A per-user IP lock.**
   - The helper writes the node admin allowlist as the user's own Webmin IP allow list.
   - Webmin checks it on every request (`check_user_ip`): `remote.cgi` answers 403 from any other address, and a login-form session opened from one gets 403 on every page.
   - The helper refuses to run without networks, and `virtualmin.yml` stops the deploy before calling it.
   - Entries carry explicit prefixes (`203.0.113.7/32`), because Webmin reads a bare `203.0.113.0` as the whole 203.0.113.x range.
3. **A firewall.**
   - `virtualmin_harden.yml` opens ports 22 and 10000 only to the same allowlist; web, mail, FTP, DNS and Usermin stay public.
   - It refuses to run with an empty allowlist, or when its own SSH connection comes from outside the list, so a deploy cannot lock Platform out.
   - It adds the allow rules before removing the old any-source rules and before the deny default, and always ends with UFW enabled.
4. **The allowlist is one setting.**
   - `infrastructure.node_admin_allowed_cidrs` holds Platform's egress addresses plus the operators' admin networks.
   - The settings write chokepoint accepts only addresses or strict networks: no host bits, no `/0`, no duplicates.
   - `AnsibleService` passes it to every playbook in normalised form.
5. **The password.**
   - It is generated by Platform and stored in the credential vault (ADR-0033).
   - It reaches the node through a 0600 vars file and the helper's stdin, never a command line.
   - The helper resets it on every deploy, so the node always converges to the vault's password.
6. **TLS.** Platform verifies the panel certificate, with optional pinning per server (`ssl_cert_fingerprint`, or `VIRTUALMIN_PINNED_CERT_SHA256`).

## Threat model

- **Platform compromised.** A compromised Platform already holds every node's root SSH key, so it owns the nodes either way. Restricting the API user would not change that.
- **A leaked API credential.** The controls are aimed here: a vault export, a log line, a backup of the vault, a stolen operator laptop.
  - With the IP lock and the firewall, the leaked password is useless from any address outside the allowlist.
- **Webmin pre-authentication bugs.** These are the other target: the firewall keeps port 10000 unreachable from the internet.
- **What the IP lock alone does not do.**
  - It refuses the requests; it does not stop password guessing. From a refused address Webmin still answers a wrong password differently from a right one: 401 against 403 on `remote.cgi`, and no session against a session on the login form.
  - The firewall closes that, and Webmin's own failed-login blocking stays on.

## Consequences

- A node cannot be deployed or hardened until `infrastructure.node_admin_allowed_cidrs` is set. This is deliberate.
- Changing Platform's egress addresses means updating the setting and re-running the node playbooks. Until then, Platform is refused by both the user lock and the firewall.
- The lab proves every control on each `make test-virtualmin-lab` run (`virtualmin_lab_checks`, check 6). vm-a stands in for a host outside the allowlist: it is refused, and with vm-a added to the list the same calls succeed.
