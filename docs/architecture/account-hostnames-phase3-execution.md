The research and task breakdown below guided the implementation. ## Source findings and decisions

The saved tasks are P3.1–P3.5 in `docs/architecture/account-hostnames-dns-mail-plan.md:298`, implementing ADR-0061 section 6. Existing seams:

- `services/platform/apps/infrastructure/dns_agreement.py`: authoritative, CNAME-aware customer routing probes; 8 hops, 8 authorities, 60-second monotonic deadline, public authority-address checks. Its repeated strict all-authority cutover agreement is stronger and more expensive than an hourly observation. Reuse transport/parsing, not three independent retry loops per component.
- `services/platform/apps/infrastructure/panel_cert_probes.py`: `public_address`, `AuthoritativeAnswer`; rejects private/special nameserver destinations. Its panel-address probe intentionally rejects CNAMEs and must retain that contract.
- `services/platform/apps/provisioning/migration_routing.py`: customer frontend snapshots/bridge retention. Monitoring must not mistake an active move for an outage or publish results gathered against the previous target.
- `services/platform/apps/api/secure_auth.py`: HMAC body identity and active membership, `require_customer_authentication` and `require_customer_role_in`. Add `TECH_ROLES=frozenset({'owner','tech'})`.
- `services/platform/apps/api/services/{views,urls,serializers}.py`: customer service reads are POST signed JSON and tenant-filter the Service lookup. Public DNS status must follow this protocol. The saved GET Platform API is incompatible with the present HMAC contract. Browser/HTMX GET remains appropriate on Portal.
- `services/portal/apps/services/{services,views,urls}.py`: `ServicesAPIClient`, `_get_session_identity`, `_get_user_role_for_customer`; role checks can fail/degrade and are not proof of current Platform membership. Existing `can_manage` includes billing and must not authorize DNS recheck.
- `services/platform/tests/api/test_service_detail_hosting.py`, `test_services_api_hides_node_details.py`, `services/portal/tests/services/test_service_detail_hides_node_details.py`: customer instructions use account names and hide assigned node addresses/hostnames. Raw DNS traces and expected node addresses stay staff-only.
- `services/platform/apps/provisioning/virtualmin_tasks.py:setup_virtualmin_scheduled_tasks`, `services/platform/apps/common/management/commands/setup_scheduled_tasks.py`, `services/platform/tests/common/fixtures/scheduled_tasks.json`: idempotent named schedule registry and exact production catalog fixture.
- `services/platform/apps/notifications/services.py:EmailService.send_template_email`: async send stores an EmailLog transactionally, enqueues on commit and has queue recovery. Use this durable outbox, not the hostname activation code's synchronous send/timestamp claim pattern.

Use a persisted per-account result and per-account bounded jobs. Do not perform DNS from the API, Portal view, model property or serializer. Alternative A (inline request checks) blocks pages and amplifies DNS traffic; alternative B (one hourly task probes every account) has unbounded runtime and starves later accounts. A small due-work dispatcher plus fenced account jobs avoids both.

## Design blockers resolved by the proposed contract

1. **Read HTTP method:** Platform `POST /api/services/<id>/dns-status/` carries signed customer_id/user_id/timestamp. `POST .../dns-status/recheck/` queues work. Portal `GET/POST /services/<id>/dns/` displays/rechecks with session + CSRF. Do not introduce GET bodies or a parallel HMAC identity protocol.
2. **Unknown is distinct from broken:** initial checks, network failures, budget exhaustion, unsupported DNSSEC policy, opaque CDN origins and registrar redirect destinations must not manufacture healthy-to-broken transitions. Persist each component's last definitive state/time separately from its current observation. A proven broken required component outranks unrelated unknown diagnostics in the aggregate; an unknown external-proxy or MX observation cannot suppress that break. If no component is proven broken but relevant components remain unknown, show unknown. First-ever unknown/broken observations never manufacture a healthy baseline. One durable incident email covers an active outage; repeated or additional failures during that incident do not create another email. Unknown observations preserve the incident until definitive recovery.
3. **External mail remains valid:** inspect and explain MX, but do not require MX to the account name before an explicit hosted-mail mode exists in Phase 5. Null MX can intentionally announce no mail; no MX can invoke SMTP's implicit A/AAAA fallback. No Phase 3 DNS writes or MX changes.
4. **DNS does not prove external HTTP redirects/CDN origins:** show `unverified` with precise component diagnostics. Do not label an apex redirect broken simply because its A record is not the hosting node. Do not infer ALIAS vs direct A solely from a flattened answer. Any retained manual proxy attestation is target/address/name-bound and cannot certify an origin changed invisibly behind a proxy.
5. **DNSSEC claim scope (owner decision):** Phase 3 promises bounded parent-DS/child-DNSKEY consistency diagnostics, explicitly recording `validation=not_performed` unless full validation is actually proven. This is not complete signature-chain validation. A configured validating resolver over verified TLS may supply separately attributed validation evidence; it is not a hidden prerequisite or a plaintext fallback. SERVFAIL never becomes a healthy answer. Deployment must allow any selected encrypted resolver transport before that optional evidence is enabled.

## Probe contract and verified primary documentation

Each component returns an immutable observation: state (`healthy`, `broken`, `unknown`, `not_applicable`), stable reason code, RR type/name, checked time, TTL and bounded evidence. Keep transport errors separate from proven NXDOMAIN/NODATA. Persist a versioned results JSON. Never turn truncated/incomplete authority sets into success.

- **Routing:** normalize IDNA/case/trailing dots, exact queried owner and type, finite visited CNAME set, maximum 8 hops, maximum 8 NS per zone. Query A and AAAA independently even on an IPv4-only controller. A missing IPv6 target requires proven absent AAAA; a foreign AAAA is a concrete routing warning. Do not apply the panel's no-alias policy to customer names.
- **Shared resource limits:** one monotonic deadline (proposed 90 seconds), one query ledger (proposed 96 wire questions, including discovery/CNAME/CAA/DNSSEC), individual query cap 3 seconds, authority/name/RRset/result-size caps. Reuse discovery and memoize identical questions within the run. The existing routing helper's per-call deadline is not a whole-account budget. Bound retries inside this budget; return unknown when it is exhausted. Proposed job timeout 120 seconds remains below broker retry.
- **CAA:** implement the RFC 8659 relevant-RRset search, following aliases during each lookup and climbing parents of the original owner until a policy appears. No policy or only nonrestrictive tags permits issuance; an unknown critical tag (flag 128) prevents claiming issuance is allowed. `issue` is relevant for nonwildcard customer certificates; `issuewild` does not replace it here. Recognize semicolon parameters; unknown accounturi/validationmethods compatibility is unknown, not blanket allow. RFC 8659 supersedes the older, different alias-parent search. [RFC 8659 section 3](https://www.rfc-editor.org/rfc/rfc8659.html#section-3), [Let's Encrypt CAA policy](https://letsencrypt.org/docs/caa/).
- **Optional DNSSEC validation evidence:** a fixed operator-configured, nonfiltering resolver may be queried via `dns.query.tls(...,server_hostname=<configured authenticated name>,verify=True,timeout=remaining)`, DO set and CD clear. `server_hostname=None` disables hostname checking in dnspython, so reject it. The pinned local dnspython 2.8.0 already supports these arguments. AD is trusted only on this configured secure channel; plain system-recursive AD is not sufficient. Otherwise report DS/key consistency with validation explicitly not performed. [RFC 4035 sections 4.6/4.9.3](https://www.rfc-editor.org/rfc/rfc4035.html), [dnspython TLS API](https://dnspython.readthedocs.io/en/latest/query.html#tls).
- **Resolver candidate:** Cloudflare's standard, nonfiltering 1.1.1.1 / 1.0.0.1 service supports DoT on 853 with authenticated name `one.one.one.one`. Keep endpoint choices configurable, public and operator-controlled. Do not silently fall back to plaintext validation. [Cloudflare DoT](https://developers.cloudflare.com/1.1.1.1/encryption/dns-over-tls/), [standard resolver addresses](https://developers.cloudflare.com/1.1.1.1/ip-addresses/).
- **DNSSEC diagnostics:** on validating failure, inspect EDE and optionally repeat CD=1 within the remaining budget, then collect parent DS and child DNSKEY to explain stale-DS/signature errors. Compare all supported DS digests against eligible DNSKEYs using `dns.dnssec.make_ds(...,validating=True)`; one valid rollover path is sufficient. Missing supported algorithms or an unproven negative DS response gives unknown. Do not equate every SERVFAIL to DNSSEC bogus. [RFC 8914](https://www.rfc-editor.org/rfc/rfc8914.html), [dnspython DNSSEC API](https://dnspython.readthedocs.io/en/latest/dnssec.html), [Cloudflare DNSSEC troubleshooting](https://developers.cloudflare.com/dns/dnssec/troubleshooting/).
- **MX:** report external routing separately; recognize null MX and invalid mixed-null MX. If checking target host validity, do not accept a CNAME as an MX target. No SMTP connections in this phase. [RFC 7505](https://www.rfc-editor.org/rfc/rfc7505.html), [RFC 2181 section 10.3](https://www.rfc-editor.org/rfc/rfc2181.html#section-10.3).

## Outstanding review before execution

Independent source/API/notification/scheduling review by dns_review found no branch blocker; its aggregate-component and immediate read-invalidation refinements are included above. Parent accepted unknown for opaque CDN/redirect origins with a precise reason, no outage email from unknown alone, and no additional user decision. A trusted validating resolver is needed only for additional secure-chain evidence, not for the agreed, explicitly limited DS/key consistency check. Do not weaken the signed-body HMAC contract, pretend all CAA parameters are supported, require hosted MX for external mail, or call unauthenticated DS/DNSKEY matching a secure chain.
