# ADR-0061 Phase 4: customer DNS implementation and verification

Implemented 2026-10-27 on `codex/adr61-phase4-customer-zones`, stacked on Phase 3 and the master SSH hardening integration. The first import accepts a customer-uploaded zone file only; no external Cloudflare-account importer. Application and provider-wire tests use controlled fixtures; no real Cloudflare zone or registrar delegation was changed.

## Execution record

The gateway, immutable import revisions, background operation checkpoints, signed API, Portal pages and staff diagnostics are implemented. Migration and recovery admission wait for pending or uncertain customer-zone mutations; read-only source checks and activation polling do not exclude an account move. Hosting ownership changes serialize with publication without transferring the independent DNS zone to another customer. Hosting termination withdraws only the managed web records.

Managed customer records share the account name's publication lock, original per-record TTL evidence, lowering confirmation, cache wait and verified restoration. New record creation commits its UUID and single-use dispatch intent before the provider call. A worker that loses the response recovers only from positive record ownership; it cannot issue a second blind create. Migration completion rechecks the observed target generation inside the ownership transaction.

Verified focused evidence includes 169 backend tests (two further delivery races require PostgreSQL), 15 PostgreSQL ownership tests with three real connection races, the real publication/completion deadlock regression, 32 provider/settings tests, 54 migration/managed-DNS/recovery tests, seven staff diagnostics/retry tests and 42 Portal DNS/navigation/privacy tests. An actual signed Platform receipt passes the Portal client and real Chromium upload, CSRF, redirect, HTMX and responsive-layout checks. Full typing passes for 648 Platform and 107 Portal source files. Final full-suite and PostgreSQL gates are tracked separately; these focused results do not certify production provider permissions.

The four new tables use the established `domain_` prefix. Domains migration `0006_hostedzone_hostedzoneimportrevision_and_more` and audit migration `0018_alter_auditevent_action` extend the trusted checksum manifest to 122 entries. No released migration was edited.

## Scope and decisions

- Implement a separate customer-zone gateway. The existing node/account-name gateway remains intentionally owner-scoped and supports A/AAAA/TXT; broadening that reconciler risks deleting customer records.
- First release supports the seven editor families in the saved plan: A, AAAA, CNAME, MX, TXT, SRV, CAA. Every uploaded record is inventoried. Unsupported types cause an explicit whole-import refusal before any provider write or nameserver instructions; a later adapter extension can preserve additional supported Cloudflare types. Never silently drop a record because the editor cannot display it.
- SOA and apex NS are deliberate provider-owned replacements and appear in the confirmation diff. Child NS/DS are delegation data, not apex infrastructure; preserve through an explicit adapter extension or refuse the import. Do not copy the old provider's DNSKEY/RRSIG/NSEC/DS and claim DNSSEC continuity. Version 1 uses an unsigned handover with old DS removal, then presents Cloudflare's new DNSSEC status/DS after activation.
- All routing records created here are DNS-only (`proxied=false`). Opaque proxy support requires a separate product/control decision. Do not change account-wide Cloudflare defaults.
- A zone belongs to a Customer and links to the hosting Service/account when records are managed for that service. `Domain` is optional: existing `Domain` requires a registrar and TLD and excludes externally registered domains. For the first release, zone enrollment is restricted to the authenticated customer's existing hosting-account primary domain. Arbitrary-zone enrollment needs separate ownership proof.
- Import is a durable versioned operation: raw upload digest, normalized inventory, proposed managed-record changes, infrastructure replacements, cross-check snapshot, confirmed revision, actor/time, provider applied revision and error/progress. Confirmation binds the exact revision. New upload or relevant edits invalidate confirmation and pending switch authorization.

## Official Cloudflare contracts verified

Base URL `https://api.cloudflare.com/client/v4`; Bearer token and JSON except documented import/export endpoints. Validate every response's `success`, required result fields and shape; HTTP 200 alone is not success. Persist account ID, provider zone ID and normalized zone name as an immutable binding; prove that binding before record writes/deletes.

Token capabilities must cover zone create/read/delete/activation plus DNS record read/write and DNSSEC read within the configured account. Current API permission labels differ between endpoint pages: create accepts `Zone Zone Edit` or `Zone DNS Edit`, activation requires `Zone Write`, DNSSEC details accepts `DNS Read` or `DNS Write`. Provision the matching modern Zone/DNS permissions using the provider's actual permission groups and prove the operations against a disposable zone; do not infer zone-create ability merely from a successful record read. The existing restricted account-name-zone token remains separate.

Payloads for the seven families: A/AAAA use `content` IP; CNAME uses `content` target; MX uses `content` target plus top-level `priority`; TXT uses RFC 1035 quoted strings; SRV uses `data={priority,weight,port,target}`; CAA uses `data={flags,tag,value}`. Include normalized name, numeric TTL and ownership comment. Priority/weight/port are unsigned 16-bit values and CAA flags one byte. Validate the precise family payload before the request. No apex CNAME; prevent CNAME/address coexistence. Use a CAA tag allowlist, preserving valid CA values rather than restricting every CAA record to one issuer. [Record creation](https://developers.cloudflare.com/api/resources/dns/subresources/records/methods/create/).

Use DNS-only numeric TTL 60–86400 in this first release, avoiding Enterprise-only minimum 30 and automatic TTL sentinel 1 in migration evidence. Uploaded values outside the supported range need an explicit proposed change in the confirmation diff or refusal. Cloudflare proxy TTL is automatic and cannot carry this numeric managed-TTL contract. [TTL rules](https://developers.cloudflare.com/dns/manage-dns-records/reference/ttl/).

Record names may contain service labels such as `_dmarc`, `selector._domainkey` and `_sip._tcp`; a web-hostname validator would incorrectly reject these. Parse DNS names and encode domain labels deliberately. Preserve TXT quoted strings/escapes; translate through typed rdata, not whitespace splitting. Cloudflare has more DNS types than this release's editor, so distinguish provider capability from our implemented adapter. Enforce provider wire/content bounds before writes. [Record types](https://developers.cloudflare.com/dns/manage-dns-records/reference/dns-record-types/).

Do not submit the uploaded file directly to Cloudflare's bulk import: its returned counts do not prove each expected record's identity/content/provenance. Parse locally and publish the exact confirmed inventory through recorded per-record operations. A provider batch also does not make authoritative propagation atomic. [Bulk import API](https://developers.cloudflare.com/api/resources/dns/subresources/records/methods/import/), [batch propagation](https://developers.cloudflare.com/dns/manage-dns-records/how-to/batch-record-changes/).

## Bounded complete zone-file parsing

The installed dnspython source is the source of truth for the adapter; do not use `dns.zone.from_file` on uploads. `from_file` allows includes by default, and Reader accepts `$GENERATE` by default. Only `$ORIGIN` and `$TTL` are allowed. `$INCLUDE`, `$GENERATE`, unknown directives, malformed input, non-IN classes and unsupported rdata fail the whole preview with file/line context. Upload and complete canonical export share a 2 MiB bound, with at most 2,000 total records and 128 values per RRset. The RRset cap matches the bounded authoritative observation transport; an inventory that cannot be verified is refused before provider writes. Per-record wire/content and per-RRset text limits also apply. No disk includes, generated expansion, truncation or silent record omission is allowed.

Two source-confirmed traps need RED tests before choosing the adapter:

1. `.venv-darwin/lib/python3.13/site-packages/dns/zonefile.py:175` silently eats out-of-zone owner lines. `from_text(origin=requested_zone)` plus post-parse containment is insufficient: it cannot detect data already discarded.
2. `dns/transaction.py:450` unions records before put hooks; duplicate records are deduplicated and differing RRset TTLs normalize. A put hook alone cannot retain the original per-RR TTL evidence or count all parsed input.

Implement a small bounded Reader/transaction adapter that sees every parsed `(absolute_owner, ttl, rdata)` **before union**. One source-compatible approach uses the normal transaction's requested-zone origin for SOA validation, sets the Reader's acceptance root to DNS root to prevent the silent skip, retains the requested zone as `current_origin`, and captures/validates each `add` before the normal merge. This adapter must be pinned by behavior tests; do not change installed library files. Explicitly check requested-zone containment for every owner; SOA must be exactly the apex. Capture raw parsed count, duplicate disposition, original TTL and source line before any deduplication. Reject conflicting TTLs within a single owner/type RRset rather than silently choosing the minimum.

Retain normalized absolute rdata targets, multiline/escaped TXT byte strings, unusual DKIM selectors, wildcard owners, relative owners and targets, omitted owners, explicit class/TTL ordering, default/inherited TTL and decimal escaped labels. Unknown RFC 3597 `TYPE#### \\# length hex` parses as generic rdata; retain it in the rejected inventory with owner/type/raw value. Do not mistake parser support for provider support. Duplicate identical RRs may be collapsed only as a visible preview normalization.

Require a complete zone export with apex SOA/NS, preserve those in the preview, and show their replacement by provider infrastructure. A file with signed apex material or child delegation that the adapter cannot faithfully publish is refused before any external write. Keep the original file private to Platform with content digest, size and retention policy; do not put arbitrary upload text or token-bearing provider responses in audit metadata or logs.

## Confirmation, cross-check and activation sequence

1. Authorize customer/account and acquire local enrollment uniqueness/lease. Save the upload and parsed draft locally. Refuse unsupported records/invalid inventory without a provider write.
2. Snapshot existing authoritative delegation and old DS; query old authoritative servers for bounded common names and names/types learned from the upload. Queries supplement the complete file. Include apex, www, mail, autodiscover, `_dmarc`, imported and common DKIM selectors and relevant SRV owners. A positively observed old record absent from the draft blocks progress. Unknown/timeouts never count as authoritative absence. Probe work runs in background tasks under a total deadline, with public-server address checks.
3. Present all inventory, infrastructure substitutions, TTL normalizations and proposed PRAHO-managed apex/www changes. Uploaded web records pointing elsewhere must not be silently replaced; customer explicitly confirms that managed-record diff along with inventory completeness. Bind confirmation to the upload/desired revision, customer and active hosting target.
4. Create the Cloudflare zone using a recorded intent and known prior absence; persist its binding immediately. Reconcile an ambiguous POST by exact account/name and pending intent, refusing to adopt unrelated/pre-existing zones. Read every provider record before deciding which owned record to create/update/delete. Unexpected unowned records block instead of being erased.
5. Publish the confirmed manifest, record every applied ID/owner/version even if later operations fail, then read back the complete provider inventory. Reconcile semantic rdata/TTL/proxy/ownership, not merely counts. A new preview revision or lease loss stops stale work.
6. Only after customer confirmation, exact provider readback and old-provider cross-check success does the FSM enter `awaiting_ns` and expose NS instructions or registrar update. An old DS must be removed before replacement; observe authoritative parent DS absence and, when captured, let its old TTL expire. After activation, display the new Cloudflare DS/status for a separate intentional enabling step. Old keys are not migrated by copying records. [Cloudflare full-setup/DNSSEC sequence](https://developers.cloudflare.com/dns/zone-setups/full-setup/setup/).
7. Registrar one-click requires a same-customer exact-name Domain, an adapter with nameserver-update capability and the same confirmation revision. Use `DomainService.update_nameservers`; pending registrar responses remain pending. External registration gets instructions only.
8. Poll both provider status and authoritative parent delegation. `active` requires the expected NS set, provider active status and complete applied current inventory. Provider pending zones may answer on their assigned servers; that alone is not proof of public delegation. [Zone states](https://developers.cloudflare.com/dns/zone-setups/reference/domain-status/).

Showing the assistant cannot prevent a customer from manually changing registrar settings outside PRAHO. The enforceable contract is that PRAHO does not offer or perform the switch before proof, and reports premature observed delegation as an actionable incomplete state.

## Managed routing: full Phase 2 contract extension

Data model: per logical managed record, retain stable local UUID, provider record ID, name/type, `managed_by`, desired/applied rdata, desired/applied TTL, proxy flag, owner tag, desired/applied revision, previous TTL and provider-confirmation timestamps. Keep provenance for deleted/replaced records long enough to restore/finish retries. A new provider record ID does not erase the stable logical slot's previous TTL. Customer data remains separate from managed state.

Lock order is account (if needed) → fresh `AccountHostname` → HostedZone rows in UUID order → HostedZoneRecord rows in UUID order. Code holding a name lock must never acquire the account lock afterward. Every managed record provider write, including enrollment activation, repair sync, lowering, restoring, withdraw, move and termination, passes through the same account-name publication lock. Request handlers only persist authorized intent; tasks re-read target/revision/ownership under that lock.

- Enrollment drafts can be prepared during a migration, but final managed-record activation/reservation must serialize with the name and refuse while an active account operation makes the confirmed target stale. Reconfirm a draft whose target or managed inventory changed.
- Managed web slots include apex A/AAAA and www A/AAAA or www CNAME to the owned account name. Do not allow customer CRUD to create a competing A/AAAA/CNAME at a managed owner or convert an imported record into an untracked shadow. Unrelated apex TXT/MX/CAA remain editable as permitted by CNAME exclusivity.
- Before cutover, snapshot **every managed frontend record's previous TTL**, including www CNAME. Lower and confirm all records under the publication lock. The account's cache wait uses the maximum original TTL across owned-name A/AAAA and managed-zone A/AAAA/CNAME; start `ttl_confirmed_at` only when every current provider record confirms lower TTL. Retry attempts and confirmation clocks remain distinct. A removed family/address replacement retains its old-TTL upper bound.
- Routine sync keeps lowered TTL on both the owned name and managed customer records. A record/zone added after confirmation invalidates the confirmation clock and either joins the original-TTL wait or is refused until the operation ends. Provider partial success preserves applied evidence and retries only the unconfirmed remainder.
- All cancellation/deadline/precommit compensation restores each record's own old TTL and confirms it before clearing evidence. Postcommit bridge cleanup restores the same evidence after routing/cache retention proof. A stale caller may not publish or clear another operation's snapshot.
- Commit keeps the account/name transition atomic. Postcommit desired writes go only toward the committed target; no compensation back to source. Extend migration convergence to required managed-record name/type/zone proofs; owned-name agreement alone is insufficient for an active managed zone that still points to source. Preserve current CNAME-chain/frontend bridge retention and source-fenced keep-target behavior.
- Customer records not marked PRAHO-managed never move or get TTL-lowered. Hosting termination withdraws only managed web slots; deleting the entire DNS zone requires separate explicit DNS deletion, because unrelated mail/verification records can still be in service.

## Concrete blockers and unresolved acceptance details

1. **No verified real customer-zone account token/permissions/quota yet.** Mock tests cannot prove the configured account can create/delete full zones or read DNSSEC. Existing account-name token is intentionally insufficient. Do not broaden or reuse it silently.
2. **Full import versus seven editor types.** The safe initial decision here is explicit whole-import refusal for unsupported records (including unsupported delegations and signed material), not a completeness claim after dropping them. Supporting them instead requires typed provider round-trip adapters and tests before that zone is accepted.
3. **Zone deletion/hosting termination policy.** Preserve customer/imported DNS data on hosting termination. Whole-zone deletion must be a separate intentional action; specify export/retention/move-away and registrar/DS behavior before exposing the active-zone delete control.
4. **Phase 3 shared API roles and client/upload seam.** Reuse its owner/tech helper and actual authenticated upload transport; do not introduce parallel identity logic. Multipart body signing must be designed/tested against the existing HMAC implementation rather than assumed to work.
5. **Parser adapter is a real implementation task.** Default dnspython zone parsing does not prove a complete inventory. Source review found silent owner dropping and early TTL merge; exact behavior regressions are mandatory before production parsing.
6. **Managed TTL extension is cross-app scope, not a final sync hook.** Phase 4 is incomplete if lower/restore/confirm/cache-age and enrollment fencing cover only AccountHostname. Include www CNAME old TTL and per-record replacement evidence.
